# Spell Checking: Implementation Plan

**Status:** PLAN (draft for an executor session). Produced by Session 64 (2026-07-10).
**Governs:** `BACKLOG.md` "Up Next" item 9 — spell checking (`BACKLOG.md:33`), ranked at Session 61's grill-me decision: **option (b), a scoped `cspell` config recipe** — do NOT build a spell-check engine.
**Scope lock:** a **declarative configuration recipe** for the third-party extension `streetsidesoftware.code-spell-checker` ("cspell" — **its published VS Code extension is GPL-3.0-or-later, NOT MIT; only the underlying `cspell`/`cspell-lib` engine library is MIT, corrected this session, §0.3**), scoping it to Quarto's prose regions so it stops flagging YAML keys, code-cell identifiers, and math as misspellings. **No bundled dictionary, no `DiagnosticCollection` of our own, no spell-check engine, no vendored/bundled cspell code of any kind** — this plan only RECOMMENDS a third-party extension for the user to install themselves (the same "companion extension" pattern this project's README already uses for Jupyter/R/Julia, §0.5), which does not implicate this MIT project's own license (no code combination occurs). This project's own `core/qmd/model.ts` region classifier (`scanRegions`) is the reference model the recipe's regex must approximate (cspell cannot call into our TypeScript parser — it only sees raw text via its own `ignoreRegExpList`/`includeRegExpList` regex mechanism, confirmed §0.3 — there is no TextMate-grammar-scope-based alternative available in cspell today).

## 0. Evidence provenance

Grounded this session across four independent tracks: firsthand `cspell` CLI testing against constructed multi-region `.qmd` fixtures, a direct re-read of this project's own region classifier, cited external research on `cspell`'s config semantics and license, and re-verification of the two pieces of prior art Session 61's grill-me named (the `quarto-dev/quarto#29` issue and the `vscode-spellright` PR) rather than trusting that session's summary from memory (Learning #6/#11 discipline).

### 0.1 This project's own prose-region model — re-read firsthand, `src/core/qmd/model.ts`

`scanRegions` (the single source of truth `findBodyLines`/`findAllCells`/`findFrontMatter` are thin views over) classifies every line into exactly one of: **YAML front matter** (only a `---` on line 0 opens it, closed by `---`/`...`), **a block or single-line HTML comment** (`<!-- … -->`), **inside a fenced code block** (```` ``` ````/`~~~`, ANY fence — not just executable `{lang}` cells; a plain ```` ```text ```` illustrative fence is skipped identically), or **a body line** (prose or a heading — everything else, INCLUDING a cell-option `#|` line's siblings only in the sense that those lines are cell-interior and never reach `bodyLines` at all, since they're inside an open fence).

**Critical nuance for this plan, found by re-reading, not assumed:** `bodyLines` is coarser than "prose." It is everything outside the four skip-regions above — which means Pandoc/Quarto **inline constructs that live INSIDE a body line are still "prose" by this project's own model**: inline code spans (`` `x` ``), inline math (`$x$`/`$$x$$`), a cross-reference attribute block (`{#fig-x}`), and a citation/cross-ref token (`@fig-x`) are all structurally part of a body line, not a separate skip-region. `maskInlineCode` exists specifically because callers (the cross-ref indexer, the math detector) need a SECOND, finer pass over body lines to mask out inline code — confirming the project's own architecture already treats "skip-region" and "non-natural-language token inside prose" as two different problems. §0.2 shows this distinction is empirically load-bearing for `cspell`, not academic.

### 0.2 `cspell` CLI — verified firsthand (v10.0.1, via `npx cspell`) against constructed multi-region fixtures

Built a `.qmd` fixture exercising every region kind (YAML front matter with a typo, an ATX heading with a typo, a prose paragraph with 6 deliberate typos, an inline code span containing a non-word token, inline math containing a non-word token, a cross-ref attribute block `{#fig-plotresult}` and a citation `@fig-plotresult`, a `{python}` cell with a `#| label:` option line and Python identifiers/string-literal typos, and an HTML comment with a typo) and ran `cspell lint` with `--language-id quarto` (the CLI's equivalent of a VS Code custom `languageId`, since `.qmd` has no built-in cspell file-type).

- **Baseline (zero custom `ignoreRegExpList`, "quarto" is an unrecognized languageId to `cspell`): 18 issues found, only 6 of which are genuine prose typos.** The other 12 are false positives: both YAML-front-matter typos, the inline-code-span token, the math token, the cross-ref label/citation token (flagged 3×, once per each of its 3 occurrences: the attribute block, the citation, and the `#| label:` cell option), the code cell's Python identifiers/string literal, and the HTML-comment typo. **Confirms empirically, not from documentation: an unrecognized custom `languageId` gets ZERO built-in markdown-aware region-skipping from `cspell`** — front matter, fenced code, inline code, math, and HTML comments are ALL checked as plain prose unless the recipe supplies its own `ignoreRegExpList`. The one exception: a URL inside a markdown link was NOT flagged in the baseline — `cspell` ignores URL-shaped tokens via a global default unrelated to `languageId`, so the recipe does not need to handle links/URLs itself.
- **With a crafted `languageSettings` override (`languageId: "quarto"`, `ignoreRegExpList` covering YAML front matter, any fenced block, inline code spans, HTML comments, and math): down to exactly the 6 genuine prose typos, zero false positives.** A sanity-check fixture (a genuine typo immediately adjacent to a citation, `@fig-plotresult`) confirmed the recipe does not over-exclude — real typos next to a suppressed token are still caught.
- **Cross-reference labels/citations (`{#fig-x}`, `@fig-x`) are a THIRD, genuinely distinct false-positive source beyond the three `BACKLOG.md` item names ("code-cell variable names, YAML keys, and math").** Matching `scanRegions`' own skip-regions exactly (front matter + fences + comments) is **necessary but not sufficient** — `{#fig-plotresult}`/`@fig-plotresult` are structurally "prose" by this project's own model (§0.1), yet are unambiguously non-natural-language tokens. Adding two more `ignoreRegExpList` entries (a generic `{...}` attribute-block pattern, and an `@word` pattern) closed this gap in the fixture with no observed over-exclusion — verified against the adjacent-typo sanity check above.
- **A genuine, empirically-found gotcha: the front-matter `ignoreRegExpList` pattern must tolerate CRLF.** A first-draft pattern (`/^---\n[\s\S]*?\n---\s*$/m`, LF-only) silently failed to match a CRLF-saved fixture (`\r\n` line endings) — the closing `---` was never found, so the ENTIRE front matter fell through to being checked as prose (a false positive on `\r\n`-saved documents, the same failure mode a Windows-authored `.qmd` would hit). Fixed by using `\r?\n` throughout, mirroring this project's OWN convention (`scanRegions`: `text.split(/\r?\n/)`) — re-verified fixed against both the CRLF fixture and a full LF regression (no change to the 6-typo result).
- **A tilde-fenced block (`~~~lang` … `~~~`) is correctly excluded by a fence pattern that matches either fence character**, matching `scanRegions`' own `FENCE_OPEN`/`FENCE_CLOSE` treatment of backtick AND tilde fences identically.
- **The validated recipe does NOT need to special-case executable `{lang}` cells vs. plain illustrative fences** — unlike this project's own `CELL_INFO` regex (which must distinguish an executable cell from a display-only ```` ```{{python}} ```` or a Pandoc `.class` block, because those get different TREATMENT inside the extension), `cspell`'s job is simpler: skip the ENTIRE fenced block regardless of what kind of fence it is, exactly matching `scanRegions`' own `bodyLines` exclusion (which is fence-kind-agnostic too — see §0.1). This means the recipe's fence-skip regex is simpler than a full `scanRegions` port, not an approximation that risks drifting from it.

**The validated recipe (final form — revised after §0.3's research corrected the enable-step, see below):**

```jsonc
// cSpell settings — add to your VS Code settings.json (user or workspace).
// Requires the "streetsidesoftware.code-spell-checker" extension (cSpell).
{
  // cSpell checks any languageId by default (cSpell.enabledFileTypes' own
  // "*": true default, §0.3) — no explicit "enable quarto" step is normally
  // needed. If you've customized cSpell.enabledFileTypes and removed the
  // wildcard, add "quarto": true to it explicitly.

  // Scope checking to Quarto's prose regions only.
  "cSpell.languageSettings": [
    {
      "languageId": "quarto",
      "ignoreRegExpList": [
        "/^---\\r?\\n[\\s\\S]*?\\r?\\n---\\s*$/m",       // YAML front matter
        "/^\\s*(`{3,}|~{3,})[\\s\\S]*?^\\s*\\1\\s*$/gm", // any fenced block (code cells + #|///| options)
        "/`[^`\\r\\n]+`/g",                              // inline code spans
        "/<!--[\\s\\S]*?-->/g",                           // HTML comments
        "/\\$\\$[\\s\\S]*?\\$\\$/g",                      // display math
        "/\\$[^$\\r\\n]+\\$/g",                           // inline math
        "/\\{[^}\\r\\n]*\\}/g",                           // Pandoc attribute blocks ({#fig-x}, {.class}, {r})
        "/@[a-zA-Z][\\w-]*/g"                             // cross-ref / citation tokens (@fig-x, @smith2020)
      ]
    }
  ]
}
```

### 0.3 `cspell` config schema, license, and built-in behavior — external research (cited)

Two independent background research passes this session, each fetching primary sources (GitHub repos/LICENSE files/manifests, cspell.org docs, the npm registry) rather than relying on training-data memory — full detail in `PROJECT_LEARNINGS.md` Learning #71.

- **License — a correction to Session 61's own "MIT" framing.** The underlying `streetsidesoftware/cspell` engine library **is MIT**. But the actual PUBLISHED VS Code extension, `streetsidesoftware.code-spell-checker` (`streetsidesoftware/vscode-spell-checker`, current Marketplace version **4.6.0**), **is GPL-3.0-or-later** — confirmed independently from both its `LICENSE` file and its manifest's `"license"` field. **Not a blocker for this plan**: this project only recommends the extension for the user to install themselves (the identical pattern `README.md:106-116` already uses for Jupyter/R/Julia, §0.5) — no cspell code is vendored, combined, or shipped, so this MIT project's own license posture is unaffected. But the plan's own language, and `BACKLOG.md`'s prior "MIT, cspell" framing (Session 61), must not repeat the inaccurate claim (corrected in both places this session).
- **`cSpell.enabledLanguageIds` is DEPRECATED** (the extension's own manifest marks it `"deprecated": true`, directing users to `cSpell.enabledFileTypes`) — Session 61's `BACKLOG.md` text named this exact (now-legacy) setting. **`cSpell.enabledFileTypes`** is the current mechanism: an object map `languageId → boolean`, defaulting to `{"*": true, "markdown": true}`. **The wildcard means any custom languageId — including "quarto" — is already spell-checked by default, with no enable step required**, for a user who has not customized this setting. The recipe (§0.2) reflects this: no `enabledLanguageIds`/`enabledFileTypes` entry is needed for the common case; a one-line caveat covers the edge case of a user who already overrode the wildcard away.
- **No built-in structural region-skipping exists for ANY languageId — confirmed from BOTH source code and a fresh empirical test, independent of this session's own §0.2 testing.** `cspell-lib`'s own default `languageSettings` array is empty; the one universal default `ignoreRegExpList` is generic noise-suppression (URLs, emails, hashes, base64) with nothing document-structure-aware. Even VS Code's OWN BUILT-IN `markdown` languageId only gets minor link/anchor/HTML-entity exclusions from cspell's bundled config — **nothing strips YAML front matter, fenced code, or inline code, even for markdown itself.** A fresh empirical test (gibberish tokens placed in front matter / a fenced code block / an inline code span, zero custom config) confirmed all three were flagged, exactly like plain prose. **This independently corroborates §0.2's own empirical finding** — via source-code reading, not just observed CLI behavior — and clarifies the gap is not "quarto-specific bad luck," it's cspell's general design: `languageId` + regex is the ONLY lever, for every language it supports.
- **TextMate-grammar-scope-based checking (which would let the recipe reuse this project's own `text.html.quarto` grammar/`embeddedLanguages` instead of hand-written regex) is not a usable cspell capability today.** An internal `cspell-grammar` package exists with a markdown grammar defined (front matter/fenced-code-aware) but explicitly does not use a real TextMate engine (no Oniguruma — "CSpell is a pure JavaScript application") and, per a source-level trace, is not wired into cspell's live validation pipeline at all — zero call sites outside its own package. No `cSpell.*` setting exposes it. Confirms `ignoreRegExpList`/`includeRegExpList` (regex-only) really is the only available mechanism, not an oversight in this plan's own research.
- **Versions**: extension v4.6.0 bundles `cspell-lib@^9.8.0`, one minor behind the `cspell-lib@10.0.1` this session's own CLI testing used (`npx cspell` resolved latest). Immaterial to the recipe — `languageSettings`/`ignoreRegExpList` are stable, long-standing parts of the config schema in both versions (verified against the current, not a historical, schema).

## 1. Executive summary (TL;DR)

Ship a **documentation-only configuration recipe** — no `src/` code, no `package.json` contribution, no new dependency — that tells a `.qmd` author how to scope `streetsidesoftware.code-spell-checker` (its engine library is MIT; the published extension is GPL-3.0-or-later — §0.3, correcting `BACKLOG.md`'s prior "MIT" framing) to Quarto's prose regions:

1. Add a `cSpell.languageSettings` entry for `languageId: "quarto"` with an `ignoreRegExpList` that skips YAML front matter, any fenced block (code cells and their `#|`/`//|` options together, since they're the same skip-region — §0.1), inline code spans, HTML comments, math, Pandoc attribute blocks, and cross-ref/citation tokens. (No separate "enable this languageId" step — cspell already checks any languageId by default, §0.3.)
2. Note the license accurately (above) and disclose the recipe's known limitations (§4) rather than presenting it as a silver bullet.

The recipe is empirically validated this session (§0.2) against a fixture exercising every region kind: **zero false positives, all 6 genuine prose typos caught**, including a CRLF gotcha found and fixed. This is architecturally the smallest "feature" this project has shipped — smaller than any prior `BACKLOG.md` item, because there is no code to write. The open question this plan resolves for the operator is **where the recipe lives**, not whether it works (§5).

## 6. Alternatives considered (rejected)

- **Build a proper Quarto-aware spell-check `DiagnosticCollection`** (an AST-driven checker using `scanRegions` directly, instead of leaning on `cspell`'s regex layer) — rejected: this is Session 61's own explicit, operator-confirmed decision (`BACKLOG.md:33`), not re-litigated here. `cspell` (its engine library is MIT; the published extension is GPL-3.0-or-later, §0.3 — either way, already installed by many users, actively maintained) already solves the hard "is this word misspelled" problem well; building a second one duplicates real engineering effort (dictionaries, suggestion ranking, locale support) this project has no comparative advantage in.
- **Bundle a curated Quarto/R/Python jargon dictionary** (`cSpell.words`/`cSpell.dictionaries`) — rejected for v1: Session 61's own explicit "no bundled dictionary" decision. A curated jargon list is an open-ended, ongoing-maintenance commitment (which packages? which stats terms? which languages?) with no operator ask; the user's own `cSpell.words` is the existing, simpler escape hatch.
- **`contributes.configurationDefaults`** — see §5(e) above; rejected on unverified-safety grounds, not merely a style preference.
- **Recommend/bundle `streetsidesoftware.code-spell-checker` via `package.json`'s `extensionPack`/`extensionDependencies`** (auto-installing or hard-requiring it alongside this extension) — rejected on TWO independent grounds, not just one: (1) the general "no manifest-level companion-extension mechanism has ever been used in this project" precedent (§0.5) the Jupyter/R/Julia case already established should hold; (2) **now that the license is known (§0.3: the published extension is GPL-3.0-or-later, not MIT), making this MIT project's own manifest actively pull in a GPL-licensed extension is a materially different, heavier association than a documentation-only "here's how to configure it if you install it yourself" recommendation** — the latter creates no dependency relationship at all. Not evaluated as a real candidate before this session's license research; explicitly rejected now that it is.
