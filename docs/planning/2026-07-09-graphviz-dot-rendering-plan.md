# Graphviz (`{dot}`) Diagram Rendering: Implementation Plan

**Status:** PLAN (draft for an executor session). Produced by Session 55 (2026-07-09).
**Governs:** `BACKLOG.md` "Up Next" item #7 (ranked lowest of the post-Posit-comparison roadmap — "narrow benefit, `{dot}`-users only") / the "Phase 7 authoring aids" graphviz rendering follow-up: *"`{dot}` is already detected and shown as source + a placeholder; rendering needs a vendored WASM dot renderer ... plus a CSP branch and an extended `buildDiagramPreviewHtml` dot path."*

## 0. How this plan was produced (evidence provenance)

Grounded firsthand, not from memory or the prior sessions' own carried-forward assumption. The BACKLOG/`NOTICE`/`PROJECT_LEARNINGS.md` Learning #23(f) text this item inherited says rendering `{dot}` "needs a separate WASM renderer + `wasm-unsafe-eval` CSP" — that is a **prior session's untested prediction**, made in passing while scoping Session 16's Mermaid-only slice. This session verified it rather than assuming it (Learning #6 discipline: read implementations, don't estimate):

- **Downloaded and executed both realistic candidate packages directly in Node** (`npm view`/`curl` against the real npm registry, confirmed reachable this session) — `@viz-js/viz` (v3.28.0, published 2026-06-03) and `@hpcc-js/wasm-graphviz` (v1.24.1, published 2026-07-04, five days before this session). Both **successfully rendered real Graphviz-generated SVG from a `digraph { a -> b }` source** when loaded and called directly — this is not a marketing claim, it is this session's own `node -e` output, real SVG returned (`<?xml version="1.0"...` / `<!-- Generated by graphviz version 15.0.0 ...` and `15.1.0` respectively).
- **Confirmed the CSP requirement precisely, not just its existence.** Grepped both packages' actual distributed bundles for `eval(`, `new Function(`, `WebAssembly.instantiate`, `WebAssembly.instantiateStreaming`, `atob(`, `fetch(`. Neither package calls plain JS `eval()` or `new Function()` anywhere. **Both call `WebAssembly.instantiate`/`instantiateStreaming`** — this is the operative fact: per the CSP Level 3 spec, *any* `WebAssembly.instantiate`/`compile` call is gated by the `'wasm-unsafe-eval'` script-src source expression regardless of where the wasm bytes come from (embedded, fetched, or otherwise) — a narrower, purpose-built exception distinct from the broader `'unsafe-eval'` (which permits arbitrary JS `eval`/`Function` and is NOT needed here). **Conclusion, empirically locked: add `'wasm-unsafe-eval'` to `script-src`; do NOT add `'unsafe-eval'`.**
- **Confirmed self-containment.** Both packages' published npm tarballs ship **no separate `.wasm` file** — inspected the full file listing of each tarball directly. Both nonetheless ran to completion in a plain `node -e` script with **no network access needed and no missing-file error**, proving the compiled Graphviz WASM module is embedded directly in the shipped JS (`@viz-js/viz`'s `lib/backend.js`; `@hpcc-js/wasm-graphviz`'s `dist/index.js`), matching this project's own established "vendor one self-contained file" convention (`NOTICE`, the Mermaid entry, Learning #23(c)/(d)) rather than needing a second vendored binary asset.
- **Confirmed the license chain, including the part the prior assumption never mentioned.** `npm view` confirms `@viz-js/viz` is MIT and `@hpcc-js/wasm-graphviz` is Apache-2.0 — but **both wrap the same underlying Graphviz C library**, and `@viz-js/viz`'s own shipped `lib/provenance.json` (a SLSA build-provenance attestation) proves firsthand that it compiles real upstream Graphviz 15.0.0 source (`gitlab.com/graphviz/graphviz`) plus `libexpat` via Emscripten. **Fetched Graphviz's own official license page directly this session:** Graphviz is licensed under the **Eclipse Public License 2.0 (EPL-2.0)** — a weak-copyleft OSI license, not MIT, and not the EPL-1.0 this plan's author initially (mis)recalled from training-data memory before checking. **This is a genuinely new category of consideration for this project:** every existing vendored/bundled asset (KaTeX, Mermaid, the TextMate grammar references) is MIT; this would be the first EPL-2.0-derived compiled artifact shipped inside the `.vsix`. EPL-2.0 permits redistributing compiled/object-code form under different terms provided the license text and (on request) source access are made available and copyright notices are retained — legally uncomplicated (many MIT/Apache projects bundle EPL binaries), but it is a **first for this project's stated "MIT-licensed... clean-room reimplementation" self-description** (`CLAUDE.md` Purpose, `NOTICE`'s own header) and deserves an explicit operator decision rather than a silent vendoring choice — flagged as §9 Q1, not decided unilaterally by this plan.
- **Measured real file sizes and compression, not estimates:** `@viz-js/viz`'s official global/UMD build (`dist/viz-global.js`) is 1,327,319 bytes raw, gzip -9 to 479,815 bytes. `@hpcc-js/wasm-graphviz`'s only build (`dist/index.js`, ESM-only) is 813,710 bytes raw, gzip -9 to 633,655 bytes. Both are smaller than the already-accepted Mermaid asset (3.56 MB raw / ~1.29 MB packaged, Learning #23(d)).
- Re-read `core/diagram-regions.ts`, `core/diagram-preview-html.ts`, `features/diagram-preview.ts`, `NOTICE`, and both diagram-preview test suites in full this session (cited by path throughout).

## 1. Executive summary (TL;DR)

## 2. The mechanism, resolved

### 2.1 Candidate decision: `@viz-js/viz` over `@hpcc-js/wasm-graphviz`

Both were downloaded, extracted, and run to completion in Node this session (§0). Both are viable. Comparison:

| | `@viz-js/viz` (recommended) | `@hpcc-js/wasm-graphviz` |
|---|---|---|
| Wrapper license | MIT | Apache-2.0 |
| Bundled Graphviz core license | EPL-2.0 (both candidates — same upstream C library) | EPL-2.0 (same) |
| Build shipped | `dist/viz.js` (ESM), `dist/viz.cjs` (CJS), **`dist/viz-global.js`** (classic UMD `<script>`-tag build, exposes `globalThis.Viz`) | `dist/index.js` (ESM only — `"type": "module"`, no UMD/global build) |
| Fits this project's existing vendoring pattern (KaTeX/Mermaid: plain `<script src>`, `globalThis.<lib>`)? | **Yes, directly** — same shape as `media/mermaid/mermaid.min.js` | No — would need a NEW `<script type="module">` webview-loading technique, never used in this project before |
| Raw / gzip -9 size | 1,327,319 / 479,815 bytes | 813,710 / 633,655 bytes |
| `WebAssembly.instantiate`/`instantiateStreaming` present (→ needs `wasm-unsafe-eval`) | Yes (confirmed) | Yes (confirmed) |
| `eval`/`new Function` present (→ would need `unsafe-eval`) | No (confirmed) | No (confirmed) |
| Render API | `Viz.instance().then(viz => viz.renderString(dot, {format:"svg"}))` — confirmed working | `Graphviz.load().then(g => g.layout(dot, "svg", "dot"))` — confirmed working |
| Maintenance | v3.28.0, published 2026-06-03 (~5 weeks before this session) | v1.24.1, published 2026-07-04 (5 days before this session) — even more current, but a young package name (the split-out successor to the older combined `@hpcc-js/wasm`) |
| Graphviz core version bundled | 15.0.0 | 15.1.0 (marginally newer) |

**Decision: `@viz-js/viz`, vendoring `dist/viz-global.js`.** The single largest risk factor for a first-of-its-kind WASM-in-webview integration is introducing *unknowns* — `@viz-js/viz`'s official global build lets this slice reuse the **exact** proven mechanism (a nonce'd classic `<script src>` tag resolved via `webview.asWebviewUri`, `globalThis.<Name>`) this project already shipped twice (KaTeX, Mermaid) and already has a passing strict-CSP unit test pattern for. `@hpcc-js/wasm-graphviz`'s marginally newer Graphviz core and Apache-2.0 wrapper license are not compelling enough to justify introducing a new script-loading technique in the same slice as a new CSP directive. Both candidates carry the identical EPL-2.0-core disclosure question (§9 Q1) — it is not a differentiator.

### 2.2 What actually changes in the render loop

Today (`core/diagram-preview-html.ts:150-160`), the `dot` branch of the per-region loop renders a static "not yet rendered" note + the raw source in a `<pre>`. This plan replaces that branch's *content* with a real render call, following the exact structural precedent the `mermaid` branch already establishes one branch above it:

```
// once, before the per-region loop (mirrors mermaid.initialize(...) being called once):
const vizInstance = REGIONS.some(r => r.engine === "dot") ? await Viz.instance() : null;

// inside the loop, replacing the current dot else-branch:
} else if (r.engine === "dot") {
  try {
    target.innerHTML = vizInstance.renderString(r.code, { format: "svg" });
  } catch (e) {
    target.className = "diagram-error";
    target.textContent = String(e);
  }
}
```

`Viz.instance()` is instantiated **lazily, once, only if at least one `dot` region exists** — unlike `mermaid.initialize()` (cheap, always called), WASM instantiation has real cost, and a document with only Mermaid diagrams should not pay it. This is the one deliberate design deviation from a byte-for-byte mirror of the Mermaid branch; flagged as §9 Q2 in case the executor session's own measurement suggests otherwise.

### 2.3 Why `findDiagramRegions`/detection needs zero changes

Read `core/diagram-regions.ts` and `test/unit/diagram-regions.test.ts` in full this session. `findDiagramRegions` already:
- Recognizes ```` ```{dot} ```` as `engine: "dot"` (`diagram-regions.test.ts:17-27`, passing today).
- Excludes non-executable forms (a plain ```` ```dot ```` fence, `{{dot}}` display form) via the shared `CELL_INFO` filter — inherited "for free" (`core/diagram-regions.ts:11-16`).
- Returns interleaved `mermaid`/`dot` regions in document order (`diagram-regions.test.ts:48-57`, passing today).

This confirms the gap is *purely* in the HTML/render layer (`core/diagram-preview-html.ts`) and the webview resource wiring (`features/diagram-preview.ts`) — nothing in `core/diagram-regions.ts` or its tests needs to change.

## 5. Interface contracts

### 5.1 `src/core/diagram-preview-html.ts` (extended, still pure/`vscode`-free)

```ts
export interface DiagramPreviewHtmlOptions {
  regions: DiagramRegion[];
  /** Webview URI of the vendored `mermaid.min.js`. */
  mermaidJsUri: string;
  /** Webview URI of the vendored Graphviz `viz-global.js`. */
  vizJsUri: string;
  cspSource: string;
  nonce: string;
}
```

CSP change (`core/diagram-preview-html.ts:51-60`), the one CSP-relevant line:

```ts
`script-src 'nonce-${nonce}' 'wasm-unsafe-eval'`,
```

No other CSP directive changes — `'wasm-unsafe-eval'` permits WASM compilation only, not JS `eval` (§0); `img-src`/`style-src`/`font-src` are unaffected (Graphviz SVG output uses no external images/fonts by default, same class of asset as Mermaid's simple diagrams — no `image=`-attribute graphs are part of this v1's test/verification scope, §3).

New script tag (alongside the existing Mermaid one, `core/diagram-preview-html.ts:119`):

```ts
<script nonce="${nonce}" src="${escapeAttr(vizJsUri)}"></script>
```

Render-script change: the per-region `if (r.engine === "mermaid") { ... } else { ... }` becomes a 3-way branch (`mermaid` / `dot` / anything else falls through unreached, since `DiagramEngine` is a closed union of exactly these two) with the `dot` branch calling `vizInstance.renderString(r.code, {format: "svg"})` per §2.2, and `vizInstance` obtained once via the lazy-if-any-dot-region pattern (§2.2) before the loop.

### 5.2 `src/features/diagram-preview.ts` (extended adapter)

```ts
private graphvizRoot(): vscode.Uri {
```

`render()` (`:88-102`) gains a `vizJsUri` construction mirroring `mermaidJsUri` (`:93-95`), passed into `buildDiagramPreviewHtml`. The webview-creation call (`:43-53`) widens `localResourceRoots` to `[this.mermaidRoot(), this.graphvizRoot()]`.

## 7. Failure-mode / risk analysis

| # | Risk | Severity | Mitigation |
|---|---|---|---|
| D1 | **`localResourceRoots` omission silently blocks the script load**, distinct from and in addition to the CSP change — VS Code webviews enforce a *second*, independent gate (which local files the webview may even request) beyond the page's own CSP. Forgetting `graphvizRoot()` in the `localResourceRoots` array (§5.2/G4) would make the `<script src>` request fail silently (a blocked-resource console message, not a thrown JS exception the extension host would see) even with a perfectly correct CSP. | Medium | The gate-d dot-open integration test (§6) would likely still pass (the panel opens; VS Code doesn't crash on a blocked subresource) — **this is a real coverage gap**, flagged explicitly rather than papered over: recommend the executor also manually confirm (or find a way to assert) the webview's devtools console is clean of resource-blocked errors during the Phase 3E runtime smoke test, since neither the unit nor the integration layer can catch this class of failure the way they catch a CSP-string regression. |
| D2 | **The EPL-2.0-core disclosure question is unresolved by this plan** — a deliberate choice (§0, §9 Q1), not an oversight, but it blocks L1 (vendoring) until answered. | Low (process, not technical) | Flagged prominently as the first open question; do not vendor the asset until it is resolved at kickoff. |
| D3 | **Version drift between this plan's pinned sha256/version and the executor session's actual download.** `@viz-js/viz` is actively maintained (published 5 weeks before this session) and could release a new version before implementation. | Low | §5.3 explicitly instructs re-download + re-hash at implementation time, matching the existing `NOTICE`/Mermaid "on upgrade, re-verify" convention — this plan's cited hash is provenance for *this session's* research, not a value to blindly copy into `NOTICE`. |
| D4 | **A malformed/invalid `dot` source throws inside `Viz.instance().renderString(...)`.** Unlike Mermaid (whose `mermaid.render` is already wrapped in the existing try/catch, §2.2's mirrored structure), an uncaught throw from Graphviz's C-level parser (surfaced through the Emscripten wrapper) could theoretically differ in shape (e.g. an `ExitStatus`-typed error, confirmed present in `viz-global.js`'s own source, §0) from a plain `Error`. | Low | §2.2's design reuses the identical try/catch shape already proven for Mermaid; `String(e)` (used today) handles any thrown value shape, including a Graphviz-specific error class — no special-casing needed, but the executor should add one test asserting an invalid `dot` source produces the `diagram-error` class rather than a silently blank pane, mirroring test coverage this project has NOT actually written for Mermaid's own error path either (a pre-existing gap, not new to this plan — worth a one-line note in the executor's own test list, not a blocker). |

## 8. Alternatives considered

| Alternative | Why not |
|---|---|
| `@hpcc-js/wasm-graphviz` as the primary vendor target | **Not rejected outright — a legitimate close second** (§2.1). Passed over because it is ESM-only (no UMD/global build), which would introduce a `<script type="module">` webview-loading technique this project has never used, in the same slice as a new CSP directive. If a future constraint makes `@viz-js/viz` unsuitable (e.g. it stops shipping a global build), this is the documented fallback — re-run §0's verification against its then-current version before switching. |
| The older, combined `@hpcc-js/wasm` package (pre-dates the `@hpcc-js/wasm-graphviz` split) | **Rejected** — superseded by the graphviz-only split package this plan already evaluated (smaller, more focused, actively maintained as the current recommended path per its own npm publish cadence). |
| Server-side rendering (spawn the user's own installed `dot` CLI, if present, instead of vendoring WASM) | **Rejected** — Quarto itself does not require a separate Graphviz install for `{dot}` cells (it vendors its own), and this extension has no existing precedent for shelling out to anything but the `quarto` binary itself; introducing a *second* external-binary dependency (optional Graphviz CLI) for one preview feature adds a whole new "is it installed / where / what version" UX surface this project's `quarto.path` configuration precedent doesn't cover. WASM vendoring keeps the feature self-contained and license-disclosed, consistent with the Mermaid precedent. |
| Rendering `dot` via a pure-JS reimplementation of Graphviz's layout algorithm (no WASM, no EPL question at all) | **Rejected** — no such reimplementation exists with meaningful fidelity to real Graphviz output (this is precisely why every mainstream "Graphviz in the browser" tool, including `d3-graphviz`, is itself a WASM wrapper around the real C library) — this is not a live option, not merely a worse one. |
| Skip the EPL question by not shipping the WASM inside the `.vsix` — fetch it from a CDN at runtime instead | **Rejected, decisively** — this project's webview CSP is `default-src 'none'` specifically so nothing is ever fetched over the network at render time (matching the Mermaid/KaTeX precedent and this project's offline-friendly design); a runtime CDN fetch would also need a `connect-src`/`script-src` origin allow-list exception, a materially larger CSP loosening than `'wasm-unsafe-eval'` alone, for a worse (network-dependent, non-air-gapped) UX. |

## 9. Open questions for the executor (resolve at implementation kickoff)

1. **EPL-2.0 disclosure sign-off (§0, D2).** This is the one question this plan does NOT resolve on the operator's behalf. Vendoring `viz-global.js` ships a compiled copy of Graphviz (EPL-2.0) inside this MIT-licensed extension's `.vsix` — legally uncomplicated to redistribute (EPL permits this in object-code form with notice + source-access terms satisfied by `NOTICE`'s disclosure + the upstream project's own public source), but it is the first time this project would do so, and `CLAUDE.md`/`package.json`/`NOTICE` all currently frame the project as unqualified-MIT. **Resolve via `AskUserQuestion` before L1 (vendoring) begins:** proceed with the EPL-2.0-disclosed vendoring as designed, or hold this item pending further license review.
2. **Eager vs. lazy `Viz.instance()` (§2.2).** This plan recommends instantiating the WASM module only when at least one `dot` region is present, unlike Mermaid's always-on `initialize()`. Confirm this is worth the small branching complexity versus simply always instantiating (mirroring Mermaid exactly) — recommend keeping the lazy form since WASM instantiation is a heavier one-time cost than Mermaid's JS `initialize()`, but this is a minor implementation-level call, not a design-blocking one.
3. **The D1 `localResourceRoots` coverage gap (§7).** No automated test in this project's existing suite would catch a webview-resource-block failure distinct from a CSP failure. Decide at implementation time whether this gap is worth closing (e.g. some `@vscode/test-electron` mechanism for reading webview devtools console output, if one exists) or accepted and disclosed at Phase 3E the same way this project already discloses other F5-only gaps (Learnings #51/#58 precedent) — do not silently skip verifying it manually at least once.
4. **One session or two?** Per SESSION_RUNNER.md's own established norm of favoring finer-grained sessions even for small items, the executor may split L1 (vendor + `NOTICE`) from L2-L4 (the actual render-path change) if preferred — both are small; recommend one session given the total surface is smaller than the already-single-session project-level-render plan.
